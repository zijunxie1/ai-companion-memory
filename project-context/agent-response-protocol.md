# Agent Response Protocol｜Founder 友好回复与决策完整性规范

> 适用：Chief、Builder、Reviewer、Release / QA 以及临时 Agent 面向 Founder 的重要回复。
>
> 目标：先让 Founder 理解正在解决的产品问题，再提供技术证据；简化表达不得导致遗漏选项、风险或好建议。
>
> **本文件是回复格式的唯一权威来源**（L1/L2/L3 分级与全部模板）；其他文件只引用本文件，不重复全文。

## 0. 回复分级总览（L1 / L2 / L3）

> 普通回复必须简短；只有少数情况才完整汇报。判断场景后按对应级别输出，不得默认输出全部内容。

| 级别 | 触发条件 | 向 Founder 展示 | 禁止展示 |
|---|---|---|---|
| **L1 普通回复** | 常规进展、确认、小范围调整 | `## 先说人话（30 秒）` 3—5 句大白话 | 完整决策看板、技术附录、测试日志 |
| **L2 普通交接** | 阶段完成需角色接力 | 先说人话 + 一张可直接复制的完整交接卡 | 重复状态报告、技术附录、重复解释"接下来会发生什么" |
| **L3 完整汇报** | 任务/重要阶段完成、阻塞、需 Founder 决策、重大风险/范围变化/权威证据冲突 | 先说人话 + 完整项目状态 + 最多三个选项 + 明确推荐 | 无（技术证据必须保留在 Markdown 交接包/附录） |

### 0.1 L1 普通确认模板（总长 3—5 句）

```markdown
## 先说人话（30 秒）

我们现在在做：……
现在的问题是：……
这一步是在：修 Bug / 完善功能 / 调整策略 / 整理规则 / 只读检查。
当前进度：……
你现在需要：不用操作 / 只决定一件事。
```

### 0.2 L1 进度模板（总长 3—5 句）

```markdown
## 先说人话（30 秒）

我们在解决：……
已完成的：……
还剩：……
当前风险：……
你现在的参与：不用操作 / 只决定一件事。
```

**L1 长度硬约束**：L1 普通回复（含进度更新）**总长度始终为 3—5 句**，只选择当前必要信息（五要素中的相关项，可不全部出现）；**七项完整状态（正在解决什么/完成什么/还剩什么/是否偏离目标/当前风险/下一检查点/Founder 是否需要参与）仅在 L3 完整汇报中使用，L1 不得展开为七项清单**。普通回复不得额外输出完整决策看板、重复状态报告、技术附录或大量测试日志。

### 0.3 L2 普通交接模板（含展示规则）

**展示规则（强制）**：普通交接的**完整交接内容写入交接文件**（含文件路径），聊天中只发**不超过 10 行的短卡**（目标角色、本次唯一目标、任务/文件路径、允许/禁止、验收、停止条件）+ 交接文件路径。完整十七字段卡用于交接文件内部，不在聊天正文展开。不得只显示语言标签而无内容框，不得拆成多个片段。Founder 应能一键复制短卡发送给下一角色，并据文件路径取用完整交接。

默认示例（短纯文本，不依赖代码框渲染）：

先说人话（30 秒）：
项目现在走到：……
当前任务在解决：……
刚完成的是：……
接下来交给【角色】做：……

直接复制给下一个角色（≤10 行短卡）：
目标角色：……
本次唯一目标：……
任务与交接文件路径：……
允许：…… ／ 禁止：……
验收：…… ／ 停止条件：……
（完整十七字段卡已写入交接文件，字段见 project-context/role-wakeup-and-handoff.md §3.1，模板见 project-context/templates/role-handoff-template.md）

### 0.4 L3 完整汇报模板

```markdown
## 先说人话（30 秒）
## 项目 → 阶段 → 任务 → 当前角色位置
## 出了什么问题
## 用户影响
## 当前做到哪
## 需要 Founder 决定什么（最多三个选项 + 明确推荐）
## 不决定会阻塞什么
```

完整汇报仅限四类情况：整个任务或重要阶段完成；出现阻塞；需要 Founder 做决定；发现重大风险、范围变化或权威证据冲突。技术证据保留在 Markdown 交接包/附录。

## 1. 核心规则

1. **先说人话**：第一部分固定为 `## 先说人话（30 秒）`；不能以 commit、文件、命令、执行模式、表格或进程日志开头。
2. **一个当前主决策，完整决策清单**：一次突出一个阻塞主线的决策，但必须登记关联决策、后续决策、建议、机会和未知问题。
3. **事实、判断、建议分开**：明确什么已核验、什么是推断、什么等待批准。
4. **说明产品影响**：必须回答“为什么做、影响谁、不做会怎样、完成后用户能看到什么”。
5. **技术细节后置**：Git、Schema、API、文件和测试放在技术附录；不得删除。
6. **状态准确**：严格区分讨论、DRAFT、APPROVED、实现、Review、MERGED、DEPLOYED、VERIFIED、CLOSED。
7. **重要结论文件化**：决策、交接和状态变化不能只存在于聊天。

## 2. 默认回复结构（L3 完整汇报用）

> **本节的完整分层结构（第零层至第四层）只用于 L3 完整汇报**（任务完成/阻塞/需决策/重大风险）。L1 普通回复见 §0.1/§0.2（总长 3—5 句），L2 普通交接见 §0.3（简短说明 + 一张完整交接卡）。**L1/L2 不得被要求附加本节的分层结构或固定状态报告**。

### 第零层：先说人话（强制）

控制在 **3—5 句**，不使用表格。必须覆盖：

1. 现在到底出了什么问题；
2. 为什么值得现在处理；
3. 这一步准备做什么；
4. 明确不会做什么；
5. Founder 现在需要决定或操作什么；
6. Agent 的推荐。

该区域禁止出现：commit SHA、Git 命令、文件路径、PR 编号、Worktree、Schema、数据库字段、状态机缩写和未解释的英文术语。

模板：

```markdown
## 先说人话（30 秒）

现在的问题是：……
如果不先处理：……
这一步只会：……
这一步不会：……
我的建议是：……
你现在只需要：……
```

判断标准：Founder 如果只读这一段，仍应知道项目在做什么、为什么做，以及应该回复什么。如果做不到，后面的技术内容再完整也视为不合规。

### 第一层：Founder 摘要

```markdown
## 你现在需要知道的

我们正在解决：
为什么重要：
当前进展：
对产品的影响：
不处理的后果：

## 决策看板

| ID | 类型 | 要决定/关注什么 | 是否阻塞 | 建议 |
|---|---|---|---|---|

## 当前主决策

推荐：
其他可选方案：
推荐依据：
你现在需要回复：

## 决定后会发生什么

1. ...
```

如果没有 Founder 决策，明确写“你现在不需要操作”，并说明下一检查点。

### 第二层：产品影响与完整性

```markdown
## 会改变什么 / 不会改变什么
## 风险、未知问题和停止条件
## 其他建议与机会（不阻塞当前主线）
```

### 第三层：技术附录

技术附录按需包含：分支、commit、文件、冲突、数据模型、API、命令、测试矩阵、回滚和原始证据。

### 第四层：下一窗口唤醒卡

如果本回复完成了当前角色阶段或需要角色接力，必须按 `project-context/role-wakeup-and-handoff.md` 提供可复制的唤醒卡。不得只写“下一步交 Reviewer/Builder”，因为休眠窗口不会自动收到交接。

## 3. 决策类型

| 类型 | 定义 | 展示规则 |
|---|---|---|
| 主决策 | 当前阻塞主线，必须先决定 | Founder 摘要中重点展示 |
| 关联决策 | 与主决策耦合，最好同时确认 | 同一决策看板展示 |
| 后续决策 | 已发现但当前不阻塞 | 登记触发时点，不反复请求 |
| 建议项 | 有明确推荐但不需批准 | 单独列出，不伪装成已决定 |
| 新机会 | 可能有价值但证据不足 | 进入机会池，不自动建任务 |
| 未知问题 | 缺少证据无法判断 | 写明补证方式和责任人 |

若同时出现多个独立主决策，Chief 必须给出依赖顺序。当前只请求最先阻塞的一项，但其余事项必须进入 `decision-register.md`。

## 4. 四类场景模板（L3 完整汇报细分）

> §4 的四类模板是 **L3 完整汇报**的具体场景细分（决策请求 / 进度更新 / 异常阻断 / 完成交接）。日常普通回复（L1）与普通交接（L2）见 §0；不得把 §4 的完整结构用于 L1。

### 4.1 决策请求

先写产品问题、影响、完整选项、推荐和不决策的后果；最后把执行模式翻译为 Founder 可理解的选择，例如：

> 这是一次性、边界清晰的整理工作，建议使用临时执行窗口。你只需确认“开始”或“暂缓”。

### 4.2 进度更新

必须包含：正在解决什么、完成了什么、还剩什么、是否偏离目标、当前风险、下一检查点、Founder 是否需要参与。

### 4.3 异常 / 阻断

必须包含：发生了什么、产品影响、是否会丢数据、已停止的动作、可选方案、推荐方案和需要的裁决。原始报错放入附录。

### 4.4 完成 / 交接

必须包含：解决了什么、用户现在能做什么、完成证据、验收结果、已知限制、下一责任人。测试通过不得单独作为“产品完成”的证明。

## 5. 外部模型复核包

重大产品、架构、范围、主线或不可逆决策必须附带可复制区块：

```markdown
## 外部模型复核包

决策 ID：
要解决的问题：
当前产品目标：
已核验事实：
不可违反的约束：
候选方案：
Chief 推荐及依据：
已知风险：
尚未确认的信息：
希望外部模型重点挑战：
相关文件与证据：
```

复核包必须允许其他模型独立反驳 Chief，不得只提供推荐方案的支持材料。

## 5.1 沟通体验验收规则（GOV-002 批准时 Founder 附加，must_add）

> 本六条规则为**回复与附件体验的强制验收标准**（GOV-002 §5.1）；交接卡格式规则见 `project-context/templates/role-handoff-template.md`。

1. **普通回复仅 3—5 句大白话**（见 §0 L1 分级）；
2. **结论、Founder 下一步操作和交接卡必须位于消息底部**，不得埋没在正文中间；
3. **完整证据、日志和长文件清单放入附件**，不在聊天正文展开；
4. **交接卡优先使用底部单个 YAML 代码框**（YAML 代码框是 Markdown 渲染容器），但仅在 Hermes 实测完整显示且可一次复制后使用；无法实测或渲染异常时必须使用纯文本；
5. **渲染异常自动退回**：如果 Hermes 出现内容截断、代码框拆分、符号外泄或无法复制，必须自动退回不超过 10 行的短纯文本卡；短纯文本卡仍被截断时，正文用一句话说明"交接卡渲染失败，请读取交接文档文件路径"；
6. **未在 Hermes 中实际验证成功，不得声称"渲染问题已解决"**。

## 6. 技术术语翻译规则

技术术语第一次出现时必须同时解释产品含义。例如：

- `main`：GitHub 默认正式代码主线；
- `PR`：先审查、后合入正式主线的受控变更申请；
- `Config Snapshot`：每次评测当时使用的模型、阈值和策略配置记录；
- `force push`：重写远端历史，存在覆盖他人成果的风险；
- `Schema Migration`：数据库结构升级步骤，可能影响历史数据和回滚。

不能以“Founder 不懂技术”为理由删除必要风险；应先翻译，再把完整证据放入附录。

### 6.1 不合格与合格示例

不合格开头：

> GOV-001 从 origin/main 创建 Worktree，merge origin/master 后解决 3 个冲突并提交 PR。

合格开头：

> 现在项目同时存在两个“正式版本”，新评测功能只在其中一个版本里。如果不先统一，后续开发可能基于不同底座，造成重复工作或成果丢失。这一步只整理代码主线，不改变产品功能。我的建议是先让 Builder 准备一个可审查的合并方案；完成后仍由你决定是否正式合入。

## 7. 回复合规自检

自检按回复分级（§0）分别执行，**不是所有回复都要求完整决策看板**：

### 7.1 L1 普通回复自检

```text
## L1 回复合规自检

[ ] 总长 3—5 句
[ ] 只含当前必要信息（五要素中的相关项）
[ ] 未附完整决策看板、技术附录或固定状态报告
[ ] 不含未解释的技术细节（commit SHA、文件路径、PR 编号、Worktree、Schema、状态机缩写、英文术语）
[ ] 已明确 Founder 是否需要操作（不用操作 / 只决定一件事）
```

### 7.2 L2 普通交接自检

````text
## L2 回复合规自检

[ ] 先说人话（3—5 句）+ 聊天短卡（≤10 行）+ 完整交接文件路径（role-wakeup-and-handoff.md §3.1）
[ ] 未附重复状态报告或技术附录
[ ] 短卡未拆成多个片段；YAML 代码框/纯文本框未泄漏符号；短卡仍被截断时已给出交接文档文件路径
[ ] 未重复解释"接下来会发生什么"
````

### 7.3 L3 完整汇报自检

```text
## L3 回复合规自检

[ ] 已先解释产品问题和影响
[ ] 第一部分是 3—5 句"先说人话"，且不含未解释的技术细节
[ ] Founder 只读第一部分也能理解并作出当前决策
[ ] 已区分核验事实、判断、建议和待批准事项
[ ] 已列出完整决策看板，没有因突出主决策而遗漏其他事项（仅 L3 使用）
[ ] 已说明会改变什么、不会改变什么
[ ] 已列风险、未知问题、停止条件和不处理的后果
[ ] 技术细节已保留在附录
[ ] 状态术语符合状态机
[ ] 重要结论已写入或明确将写入哪个项目文件
[ ] Founder 当前需要做什么已经明确；无需操作时也已说明
[ ] 需要角色接力时已提供下一窗口唤醒卡（含完整十七字段交接卡），没有暗示自动接力
[ ] 没有把规则文件、Reviewer 或休眠角色描述成常驻自动监督
[ ] 已输出固定状态报告（handoff-and-task-state-machine.md §9，仅 L3 使用）
```

### 7.4 总则

如果任一关键项无法满足，Agent 应修正回复或明确说明缺少什么，不能假装合规。**L1/L2 不得被要求附加完整决策看板、技术附录或固定状态报告；这些仅属于 L3。**

## 8. 合规边界

Markdown 规则本身不能保证模型永远遵守。项目通过以下证据门降低失效概率：

1. `AGENTS.md` 强制引用本协议；
2. 新窗口和上下文恢复必须提交启动回执；
3. 重要结论必须写入仓库文件；
4. 交接文件必须包含 `required_reading`；
5. Founder 唤醒 Reviewer 后，Reviewer 在 Review 门追溯检查过程合规并可打回；
6. `current-state.md` 与 `decision-register.md` 提供压缩后恢复入口。

上述机制不构成常驻监督。当前没有被 Founder 唤醒的角色不会主动读取文件、检查进度或更新状态。
