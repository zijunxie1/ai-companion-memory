## 1. 一页背景：这是什么项目、为什么现在需要决策

TASK-003 是 AI Companion Memory OS 的评测能力建设。评测台用一组固定 Case 比较 Before Baseline 与 After Baseline，目标不只是展示分数，而是回答三个实际问题：

1. 新版本相对旧版本变好、持平还是变差；
2. 是否违反隐私、安全、删除合规等不可妥协的强约束；
3. 结论能否追溯到 Case、Trace、Memory 写入和判定规则。

本任务经历了两个阶段：

- 第一阶段完成了一套 8765 静态单页原型，用于验证 V2 的视觉、排版和交互方案。
- 第二阶段将方案落实到 3000 端口的真实产品评测台，并接入实际数据库、评测 Case、Trace 和 Memory 服务。

静态原型的视觉审计已经通过，但用户在真实产品复审时提出了更关键的问题：页面里的“发现”“GSB”“强约束”和“评测指标”究竟从哪里来，是写死、人工判断、程序规则，还是模型分析；以及这些结论是否真的能支持日常使用。

进一步检查发现，当前问题已不仅是 UI 文案：异步 Memory 写入没有可靠终态、部分 Case 可能共享评测用户、缺少证据时的 `FAIL/NOT_TESTED` 语义不清，以及危机表达是否允许进入长期 Memory 都需要产品级决策。因此 Builder 提交了第三轮修复计划，当前仍处于**计划待确认、尚未开工**状态。

## 2. 两个页面的关系

| 地址 | 定位 | 数据 | 后续处理 |
|---|---|---|---|
| `http://127.0.0.1:8765/index.html` | V2 静态设计原型 | 内联固定快照，主要验证视觉与交互 | 冻结为设计参考，不继续建设成第二套产品 |
| `http://127.0.0.1:3000/eval` | 实际产品评测台 | 数据库、Eval runner、Trace、Memory 服务 | 本轮真正实施和验收的对象 |

两个页面 UI 不完全一致，是因为前者是交互设计基准，后者才是工程产品。正确方向不是长期维护两份前端，而是让 3000 端口产品吸收规范中有效的视觉与交互原则，同时保持真实数据链路。

## 3. 术语说明

- **Case**：一条固定评测场景，例如记忆召回、删除、隐私或安全场景；当前共 E001–E008 八条。
- **Baseline**：用来比较的基线版本；After 与 Before 的差异决定相对变化。
- **GSB**：Good / Same / Bad，只说明新版本相对基线变好、持平或变差，不等于绝对合格。
- **强约束**：隐私、安全、删除合规等底线规则；即使总体得分提升，违反强约束仍应阻断发布。
- **Trace**：一次对话及其 Memory 召回、写入、延迟、版本等可审计证据。
- **NOT_TESTED**：本次没有足够前置条件或证据完成判断；它不同于 PASS，也不同于确认失败。
- **CR**：需要产品或架构负责人明确批准的 Change Request，Builder 无权自行视为通过。

## 4. 当前已知问题

| 问题 | 现在的风险 | 本轮处理 |
|---|---|---|
| Memory 异步写入没有明确终态 | 评测器可能因固定等待时间不同而误判 | CR-C：建立 pending/completed/failed 协议 |
| 危机表达可能被写入长期 Memory | 形成严重的安全、隐私与用户伤害风险 | CR-A：策略拦截，但保留审计 Trace |
| Case 可能共享评测用户 | 前一条 Case 的 Memory 污染后一条结果 | 每条 Case 使用独立 eval_user_id |
| 证据缺失与失败混用 | E006 等场景可能出现虚假的 PASS 或 FAIL | 判定升级为 PASS/FAIL/NOT_TESTED 三态 |
| 时间字段缺少时区语义 | Run 与 Trace 可能发生 8 小时偏差或排序错误 | 历史 UTC 数据显式迁移至 TIMESTAMPTZ |
| E001 关键词不完整 | “小橘”等召回验证可能被错误判定 | 通过新增迁移修正评测数据 |
| 指标看起来永久写死 | 用户不知道指标能否扩展以及由谁维护 | 本轮标注为当前模板；配置化拆至 CR-B 后续任务 |

## 6. 需要 Chief 决定的变更

### CR-A：危机表达禁止持久化

建议：批准。

业务规则：用户输入命中自伤、自杀等危机表达时，系统仍应生成安全回复并记录 Trace，但不得把该轮内容写入长期 Memory。

批准后的产品含义：

- 这是产品安全策略，不是评测页面临时“做绿”的特例。
- 初始实现可以使用明确、可测试的规则匹配；后续可升级为独立安全分类器。
- Trace 必须明确标记 `skipped_crisis`，不能与普通“成功执行但写入 0 条”混淆。

### CR-C：Memory 写入终态协议

建议：批准。

业务规则：评测器不能再通过等待固定时间或比较 Memory 前后差值来猜测写入是否完成；产品接口必须给出明确终态。

批准后的状态语义：

- `pending`：写入尚未结束。
- `completed`：流程已结束，包括正常写入 0 条。
- `failed`：写入流程失败，并保留错误原因。
- 危机策略拦截：`completed + skipped_crisis`。
- 评测等待超时：评测结果显示 `NOT_TESTED`，不得猜测为成功或失败。

### CR-B：评测指标配置化

建议：批准拆分至后续 TASK。

本轮只交付固定评测模板，但 UI 应明确写成“当前评测模板”或等价表达，避免造成指标永久写死的产品承诺。

后续任务应讨论：

- 谁可以创建、编辑和停用指标；
- 指标属于全局、评测集还是单次 Run；
- 强约束是否可配置、由谁审批；
- 指标版本和历史 Run 的可复现性；
- 人工评分、程序规则与模型评审之间的权责边界。

## 7. 为什么本轮需要这些改动

用户复审提出的核心问题不是单纯视觉问题，而是页面中的判断是否有真实数据链路和可解释来源：

- “本次评测发现”不能像写死文案；必须能追溯到固定快照、规则结果或人工/模型分析来源。
- GSB 是相对 Baseline 的结果分类，不等于绝对质量是否合格。
- 强约束必须有明确规则、证据和未测试状态，不能把证据缺失显示为通过。
- Memory 异步写入若没有终态协议，任何持久化评测都有误判风险。
- 评测指标目前固定可以接受，但不能暗示未来永远只有这五项。

因此，本轮目标不是继续美化静态原型，而是让 `http://127.0.0.1:3000/eval` 的真实评测链路诚实、可追溯、可重复。

## 8. 不在本轮范围内

- 不继续修改或扩展 8765 静态原型。
- 不实现用户自助新增、删除、编辑评测指标。
- 不把“本次评测发现”升级为在线大模型自动根因分析系统。
- 不修改产品 Chat、Memory 管理、Trace 日志三个页面的产品交互，除非是完成已批准数据协议所必需的接口改动。
- 不修改已有迁移文件，不篡改历史 Run 来制造验收通过。

## 9. 放行前的强制技术条件

以下条件属于批准后的实施边界，而不是 Builder 可自行降级的建议：

1. 绝对结论使用 `PASS / FAIL / NOT_TESTED` 三态；强约束缺少证据时不能被普通程序失败覆盖。
2. 每个 Case 使用独立 `eval_user_id`，并在结果中持久化，避免 Case 间 Memory 污染。
3. Trace 创建时即原子写入 `pending`；终态必须包含完成、失败或策略跳过的可解释结果。
4. 失败保存错误信息；超时显示 `NOT_TESTED`，不得回退到 Memory 差值推断。
5. 历史无时区时间字段迁移为 `TIMESTAMPTZ` 时，显式按 UTC 解释旧值。
6. 新增独立迁移文件，不改写已经应用的旧迁移。
7. 使用真实数据库和 Memory 服务完成至少两次全新评测 Run，不能只依赖 Mock 或静态数据。

## 10. 完成定义

只有同时满足以下条件，第三轮修复才可标记为完成：

- E001–E008 全部运行，且每条 Case 都能追溯独立用户、Trace、规则结果与最终判定。
- E007 危机表达未进入长期 Memory，Trace 明确显示策略拦截。
- E006 在缺少必要测试前置条件时诚实显示 `NOT_TESTED`，不是 `PASS` 或伪造的 `FAIL`。
- GSB 相对结论和绝对结论同时展示，用户能理解两者区别。
- “本次评测发现”明确数据来源及“原因假设”性质。
- BC005 显示“未提供”，不存在错误链接。
- 两次全新 Run 结果可重复，无跨 Case 污染和异步时序误判。
- 自动测试、构建、浏览器核心流程和控制台检查全部通过。
- 不启动重复开发服务器或监听进程，不产生反复的历史进程通知。

## 11. 实施、复审与责任边界

批准后交接关系如下：

1. Chief 只批准业务规则、架构边界和本轮范围，不代替 Builder 做技术实现。
2. Builder 按同目录下 `BUILDER-HANDOFF-TASK-003-ROUND3.md` 实施，并提交真实运行证据。
3. Builder 完成后，由独立 Reviewer 复核代码、迁移、两次全新 Run 和 Browser 操作。
4. 若最终结论为 `CHANGES_REQUESTED`，Builder 只修复明确缺陷；新增范围重新走 CR。
5. 本轮完成后，再为 CR-B 建立独立任务，讨论指标管理和模型/人工评审机制。

无需在开工前再做一轮对抗评审。对抗评审应放在真实代码和数据产出之后，否则只能重复评计划，发现不了时序、污染和证据链问题。
