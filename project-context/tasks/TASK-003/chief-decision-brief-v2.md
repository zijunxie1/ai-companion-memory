- 评测结果怎样生成和持久化；

- GSB 和强约束如何参与发布决策；
- 指标和 Rubric 如何新增、修改、冻结与回溯；
- 用户如何从结论进入确认、指派、复测和关闭问题的闭环。

因此，“页面符合 V2 Spec”与“产品机制足够好用”并不等价。

## 5. Chief 需要做的决策

### 决策 A：本轮到底要交付什么

#### 方案 A｜冻结为静态作品集原型

- 当前页面作为“评测结果展示 Demo”。
- 保持固定快照和人工结论，不建设真实运行系统。
- 只修正编号冲突与说明文案。
- 优点：最省时间，符合“作品集 Demo，不做生产级系统”。
- 缺点：面试官追问自动评测、数据链路和持续回归时，只能用方案说明回答。

#### 方案 B｜8 Case 最小真实纵向闭环（Reviewer 推荐）

- 真实执行/导入一次 Eval Run。
- 程序规则判定确定性指标；LLM Judge 处理主观维度；人工确认高风险与分歧项。
- 结果持久化后由页面动态聚合。
- GSB、强约束、Issue 和指标能够筛选与钻取证据。
- 指标使用版本化固定模板；暂不建设通用指标编辑器。
- 优点：能证明真实 PM 评测闭环，范围仍可控。
- 缺点：需要数据模型、API、Judge Spike、人工校准和多轮联调。

#### 方案 C｜通用评测平台

- 支持任意指标增删改、规则编辑、团队协作、趋势与发布门。
- 不推荐当前选择：与作品集目标相比明显过度建设，风险和时间成本最高。

### 决策 B：程序、LLM、人工的责任边界

推荐：

| 内容 | 默认责任方 |
|---|---|
| 隐私正则、字段存在性、删除后召回、确定性阈值 | 程序规则 |
| 自然度、连续性、原因候选、问题摘要 | LLM Judge |
| Safety、高风险、LLM/程序冲突、最终发布判定 | 人工确认 |

LLM 不应无审计地产生最终强约束结论。

### 决策 C：指标是否可配置

推荐先批准“版本化模板”，不批准通用编辑器：

- 项目级配置指标和 Rubric；
- 每次 Run 绑定 `eval_policy_version`；
- 修改只影响未来 Run；
- 历史使用过的指标只能归档，不能删除；
- 结果页只读，配置入口进入独立页面。

### 决策 D：统一 E007/E008

必须由 Chief/用户指定唯一映射。未裁决前，不应合并相关数据为正式事实。

## 6. 推荐方案 B 的最小验收标准

如果 Chief 选择方案 B，建议下一版只有以下闭环：

1. 能创建或导入一个真实 Eval Run，包含 8 条 Case。
2. 摘要、GSB、Issue 和指标全部从该 Run 的持久化结果计算，不在页面重复写死。
3. 每条评分和结论展示来源：程序、LLM 或人工，以及对应版本。
4. 强约束展示完整集合；没有样本显示 `NOT TESTED`，FAIL 可以阻断发布结论。
5. GSB 卡片点击后过滤 Case；Issue、指标和约束可跳转到证据 Case。
6. LLM Judge 输出必须保存评分理由、模型版本、Prompt/Rubric 版本。
7. 8 条 Case 全部人工复核；扩展到 20 条后再计算一致性并使用 kappa 阈值。
8. 人工可确认或覆盖 Judge 结果，覆盖操作留下理由和时间记录。
9. 历史 Run 不因指标或 Rubric 更新而改变。
10. 375px、键盘、对比度、触摸目标、控制台等原有护栏继续通过。

明确非目标：

- 不做任意公式/任意规则的通用编辑器；
- 不做实时流式 Dashboard；
- 不做多人权限和复杂审批；
- 不先扩 20 Case 再补真实链路；
- 不用 Mock 假装 Run、Judge 或 Trace 已接入。
