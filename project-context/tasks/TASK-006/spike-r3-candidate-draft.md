## 3. 方案 A：零新增依赖基线（mem0 2.0.13 阈值能力）

### 3.1 定位

零新增依赖基线：只使用项目当前 mem0 2.0.13 已具备的阈值能力（Python API `threshold` 参数 + 应用层现状过滤），不引入任何新依赖、新模型、新权重。目的是量化"mem0 现有能力"的真实边界，为方案 B/C 提供同口径对照基线。

> **诚实声明**：第一轮已证明"单一分数 + 单一阈值"无法可靠分离（R1/R3）。方案 A 不预设"能解决问题"，其价值是实测：应用层 0.35 与校准定阈值在固定候选池上的判断质量、mem0 原生 threshold 的端到端召回行为、零条返回、误删风险。

### 3.2 方案 A 拆两个实验角色（关键：主/补充实验分离，结果分表）

> 方案 A 有两个不同层面，必须分开测、分开报告，**不得混在一张指标表**（Founder 打回意见 3）。

**（A-主）固定候选池判断器**：方案 A 在**与 B/C 完全相同的冻结候选池**上，用"检索分数 + 阈值"做相关性判断。对比两种阈值：现状 0.35（✅ 已核验）vs 校准集确定的阈值。判断质量（F1/分离边际/误删率/零条准确率/保留数量）进入**主实验指标表**。

**（A-补）Mem0 原生阈值端到端召回**：单独测 mem0 Python API `search(threshold=t)`（🔬 待实测）对**召回阶段候选池**的改变——因为 threshold 发生在召回阶段，可能改变"哪些候选被召回"，这与"固定候选池上比较判断器"是两回事。输出进入**补充实验指标表**，含：不同 threshold 下召回候选集合变化、端到端零条行为、召回阶段延迟。

### 3.3 验证项（🔬 全部待 Spike 实测，主/补分表）

| # | 验证项 | 实验归属 | 可执行定义 |
|---|---|---|---|
| A-1 | 应用层 0.35 vs 校准定阈值（固定候选池判断质量） | **主实验** | 同一冻结候选池，两阈值分别判保留/过滤 → P/R/F1/分离边际/误删率 |
| A-2 | mem0 原生 threshold 端到端召回行为 | **补充实验** | Python API `search(threshold=t)` 逐阈值测召回候选集合变化、零条行为、召回延迟 |
| A-3 | 无真正相关记忆时能否返回零条 | 主+补分别测 | 主：固定候选池全无关时判 0 条；补：threshold 过滤后空 results |
| A-4 | 提高阈值造成相关记忆误删的风险 | 主实验 | 阈值提高时正向候选（0.445–0.660 区间边缘相关）被删比例与关键记忆漏掉情况 |

## 4. 方案 B：本地 Cross-Encoder 相关性重排（**只批准为待比较方向**，不批准具体模型）

### 4.0 方向与批准边界

- **方向依据**（📖）：cross-encoder 将 query+memory 拼接后联合编码，直接输出相关性分数，可建模"同一记忆在不同 query 下相关/无关"（对应 R1）；本地 ONNX 推理零外发；mem0 2.0.13 内置 reranker 与 fastembed `TextCrossEncoder` 均为可用接口方向。
- **⚠️ 批准边界**：本 DRAFT **只批准"本地 Cross-Encoder 重排"为待比较方向，不批准任何具体模型或权重**。任何候选进入实验，都必须：预装检查核验 + 模型事实报告（名称/版本/哈希/许可证/缓存来源/运行接口/资源需求）→ **Founder 明确批准下载/使用**。
- **BGE-reranker-base 与 BGE-reranker-v2-m3 不得混为一谈**；**不得在无本机实测前宣称某个必然更快或更好**（🔬 待实测）。
- **本机现无任何 reranker 权重缓存**（✅ 第二轮 P5-A 已核验）→ 任何候选均涉及**下载授权**，由 Founder 决定；不批准"只下载 BGE-reranker-base"单点方案。

## 5. 方案 C：外部大模型相关性裁判（**效果上限对照**，不代表获准进入生产）

### 5.0 定位与边界

- **定位**：效果上限对照——回答"若允许外部大模型裁判，相关性判断效果能到什么水平"；**不代表获准进入生产**；
- **真实用户记忆是否外发属于后续 Founder 决策**；本 Spike **只能使用合成数据**；
- **外部调用属于后续决策门**：本 DRAFT 不请求批准外部调用授权；方案 C 进入实验需单独 Change Request + Founder 批准（含数据外发政策裁决）。

### 5.1 使用现有哪一个外部模型或接口（✅ 已核验项目事实）

| 候选接口 | 事实 | 备注 |
|---|---|---|
| **DeepSeek OpenAI 兼容接口**（现有） | `LLM_BASE_URL=https://api.deepseek.com/v1`、`MEM0_LLM_MODEL=deepseek-chat`（`v2/app/.env.example`；容器 env 已核验） | 项目已配置的现有外部模型接口；mem0 容器内 `llm_reranker` 亦可配该接口（📖） |
| Dify Chatflow（现有） | `DIFY_API_URL=http://localhost:5001/v1` | 现有编排接口；非裁判默认用途，仅记录不默认采用 |

> 若实验进入方案 C，默认使用现有 DeepSeek OpenAI 兼容接口（模型 `deepseek-chat`）；接口/模型变更需 Founder 批准。

### 5.2 一次判断整批 vs 逐条调用（优先批处理）

- **优先设计**："一次提交 query + 全部候选，一次返回判断"（不默认逐条调用）；
- 单次请求：`query` + 全部候选文本（冻结候选池 top5）→ 返回每条候选的 相关/不相关 + 相关性分数；
- 逐条调用仅作对照记录（延迟/费用对比），不默认采用；
- 预计调用次数 = 批处理每查询 1 次 / 逐条每查询 N 次；费用 = 调用次数 × token × 单价；延迟 = P95 实测（🔬 全部待实测）。

### 5.3 发送哪些合成内容

- 仅发送：冻结查询文本 + 冻结候选记忆文本（合成数据、评测专用 user_id）；**不发送任何真实用户记忆、会话、user_id**；
- 输出要求：结构化（如 JSON）——每条候选 `{id, label: relevant|irrelevant, score: 0-1}`；允许全部判不相关 → **返回零条**。

### 5.4 输出：相关性分数（不称"置信度"）

- 采用 mem0 `llm_reranker` 内置评分 prompt 模式（📖：0.0-1.0 打分，0.0-0.3 = 不相关；temperature=0）或自定义裁判 prompt（含 `{query}` + `{documents}` 占位符）；具体 prompt 设计时确定并随机制冻结；
- **输出统一称"相关性分数"（0-1）**；**只有引入校准方法（在校准集上把模型原始分数映射到校准后相关性概率，如 isotonic / Platt 校准），才可称"校准后置信度"；无校准则不得称"置信度"**（Founder 打回意见 5）；
- 决策阈值仅在校准集确定（🔬 待实测）。

### 5.5 验证项

1. 同一冻结候选池上，F1 / 分离边际 / 零条准确率 / 误删率（与 A-主/B 完全同口径，主实验指标表）；
2. 延迟：批处理与逐条两路径 P50/P95（实测，不预设淘汰阈值）；
3. 费用：单轮调用次数、token 消耗估算、单价估算（📖 公开定价为线索，🔬 实测为准）；
4. 外部调用比例：方案 C 必然 100% 外部调用（与 A/B 的 0% 对照）；失败/超时回退如实记录（keep-all 回退会恢复 E004 缺陷，不得表述为修复）；
5. **数据外发声明**：本 Spike 仅合成数据；真实用户记忆外发属后续 Founder 决策。

## 6. 统一实验设计要求（主实验与补充实验分离）

### 6.1 实验结构（关键：两个实验分开，结果不混表）

```text
主实验：固定候选池判断器对比
  ├─ 方案 A（判断器形式：检索分数 + 阈值）
  ├─ 方案 B（cross-encoder 相关性分数 + 阈值）
  └─ 方案 C（外部模型相关性分数 + 阈值）
  → 同一冻结候选池，只比"判断质量"（§6.3 主实验指标表）

补充实验：Mem0 原生阈值端到端召回行为
  └─ 方案 A（Python API search(threshold=t)）
  → 单独测"召回阶段候选池变化 + 端到端零条 + 召回延迟"（§6.3 补充实验指标表）
```

> **"完全相同的候选池"只适用于主实验（三种判断器的比较）**；Mem0 原生 threshold 发生在召回阶段、可能改变候选池，因此**必须作为补充实验单独测，不得与主实验混在一张指标表**（Founder 打回意见 3）。

### 6.2 冻结候选池最低规模与类别分布（新增，Founder 打回意见 5）

> 一个"候选对" = 一条 query + 一条候选记忆（带相关性标签）。冻结候选池 = 全部候选对的集合，S1 冻结时哈希锁定，三方案共享。

| 类别 | 定义 | 最低数量 |
|---|---|---|
| 明确相关 | query 与记忆语义直接相关，应保留 | ≥ 8 对 |
| 明确无关 | query 与记忆语义无关，应过滤 | ≥ 8 对 |
| 容易混淆 | 多义词 / 他人属性 / 语义隐式关联 / 未见过表达（第一轮失败类型） | ≥ 8 对 |
| 应返回零条 | 某 query 下全部候选均为无关（整场景应返回 0 条） | ≥ 3 个场景 |
| 关键记忆不得漏掉 | 正向 Case 中不得漏掉的核心记忆（独立门保护） | ≥ 5 条 |

- **候选对总数 ≥ 30 对**（不含"应返回零条"场景内的无关候选）；
- 以上为 DRAFT 规定的最低门槛；S1 冻结时据此扩充并哈希锁定，具体文本不复用第一轮 H1–H4 原文、第二轮骨架原文、E001–E005 原文；
- 类别分布用于保证三种判断器在"难/易/零条/关键"各档都有可比较样本，避免样本偏斜造成假高分。

### 6.3 指标集（主/补分表，全部必报）

**主实验指标表（三方案判断器同口径）**：

| 类别 | 指标 | 口径 |
|---|---|---|
| 质量 | 相关记忆召回率 | 关键/相关记忆有没有被错误删掉（E001/E003 正向逐轮） |
| 质量 | 无关记忆拦截率 | E004 类无关候选被剔除比例 |
| 质量 | 零结果准确率 | "应返回 0 条"场景返回 0 条的比例 |
| 质量 | 误删率 | 应保留的相关记忆被删除的比例 |
| 质量 | Precision / Recall / F1（必要时 AUPRC） | 校准集 + 冻结 holdout 分别报告；样本量诚实声明 |
| 行为 | 每轮最终保留的记忆数量 | 三方案分别记录（对照是否过度删除） |
| 性能 | P50 / P95 额外延迟 | 预热 5、N ≥ 30、P95 = ceil(0.95×N)；增量 = 处理组 − 基线；不预设淘汰阈值 |
| 成本 | 单轮费用 | A/B 本地 0 元；C 按调用次数×token×单价估算 |
| 成本 | 外部模型调用比例 | A/B = 0%；C = 实测 |
| 资源 | CPU / 内存 / 磁盘占用 | 峰值 RSS、CPU 耗时、权重/缓存磁盘占用 |
| 失败 | 失败与不确定样本清单 | 超时、异常、低分、判定翻转逐条记录 |

**补充实验指标表（仅方案 A 端到端）**：

| 指标 | 口径 |
|---|---|
| 不同 threshold 下召回候选集合变化 | 逐 threshold 记录"召回哪些候选 / 丢失哪些候选"，对比固定候选池 |
| 端到端零条行为 | threshold 过滤后空 results 的场景与比例 |
| 召回阶段延迟 | 各 threshold 下 recall 阶段 P50/P95（与主实验判断器延迟分开） |

> 主实验与补充实验的延迟、候选集合、零条结果**分别成表，不合并**。

### 6.4 "关键相关记忆不得漏掉"独立门（防止多删拿高分）

- 验收不得只有 F1。独立门：在冻结候选池的正向场景中，**指定关键相关记忆（≥ 5 条，来自 E001 失眠↔橘猫、E003 小橘 等已批准正向关联）在冻结机制下必须被保留**；
- 任一方案漏掉关键相关记忆 → 该方案**独立门不通过**（即使 F1 高分，可能靠多删获得）；
- 独立门通过条件、关键记忆清单与判定规则在 S1 冻结时锁定，三方案同标准。

### 6.5 数据与网络边界（沿用前两轮纪律）

- 仅合成评测数据 + 评测专用 user_id；不读取/复制/落盘真实用户内容；禁止非 loopback 网络（方案 C 外部调用除外——若获批，单独审计其发送内容与白名单）；
- 零外发种子写入走容器内 `add(..., infer=False)`；REST `POST /memories` 禁用；种子运行后立即清理并核验清零；
- fetch 包装审计 + 容器网络面核验 + docker diff 零产品改动证据。
