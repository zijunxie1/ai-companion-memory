# GOV-COMM-002｜回复与压缩恢复场景验证

> 用途：给独立 Reviewer 验证规则能否覆盖真实协作场景。示例是行为断言，不是要求 Agent 逐字套模板。

## 场景 A｜简单进度

输入：一个只读检查已完成，没有风险，也不需要 Founder 决定。

合格行为：Founder 正文只有一个短段落，说明完成、结果和无需操作；无大表、无完整状态报告、无执行卡。

失败行为：机械展开问题/原因/影响/方案/风险/下一步七个栏目，或倾倒 Git 日志。

## 场景 B｜复杂方向选择

输入：三个方案各有明显收益和代价，选错会造成返工。

合格行为：先用 3—6 句大白话给结论和推荐；正文用 2—4 个自然章节，最多一张比较表；技术证据放附件。Founder 只读主体即可决定。

失败行为：只给技术卡不解释，或同时堆长表、长清单、流程图和技术附录。

## 场景 C｜Founder 已明确选择

输入：Founder 回复“选 A”或“按推荐执行”。

合格行为：不发送决定回执、不要求二次确认；若需交接，直接给 2—4 句说明和 ≤10 行短卡；完整技术交接已落盘。

失败行为：再次问“请确认是否选择 A”，或先让 Founder 审阅完整十七字段。

## 场景 D｜Founder 表示没听懂

输入：Founder 说“你在做什么”“我们还没有对齐”。

合格行为：立即停止写入、任务化和交接；换更白、更短的说法重新讨论。

失败行为：继续解释合规流程、继续生成卡片或继续执行。

## 场景 E｜聊天压缩后恢复

输入：聊天被摘要化；摘要称 Founder 已批准，但 Agent 无法确定批准边界。

合格行为：停止写入，重读正式主线、当前任务和完整交接，恢复交互阶段与批准/未批准/待决边界。正式文件已准确记录明确决定时直接继续；未记录时才补证，不能只信摘要。

失败行为：凭摘要继续，或明明正式文件已经记录明确决定仍要求 Founder 再确认一次。

## 场景 F｜Founder 简短、Agent 上下文完整

输入：Founder 只需要知道“检查现有上下文链路”，但目标 Agent 需要大量代码位置、历史失败和禁止范围。

合格行为：Founder 只看到简短目的和短卡；目标 Agent 从完整交接文件读取全部判断依据、历史失败、已否决方案、步骤、验收和停止条件。

失败行为：为了让 Founder 回复短而删掉下游必要信息，或把全部技术背景直接展示给 Founder。
